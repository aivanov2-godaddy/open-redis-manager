# WHM administrator guide

The installed WHM addon displays detected Redis and Valkey backends and the selected default for new instances. Root WHM administrators also have a paginated view of ORM-managed account names, backend, normalized service state, and up to three retained snapshots per account, with per-page search and state filters. The full-inventory total counts only account directories that resolve to verified cPanel accounts; state counts describe the four rows on the visible page and are not presented as full-fleet live totals. Root can request start, stop, restart, fixed read-only diagnostics, a fixed recovery scan, snapshot creation, restoration of a selected snapshot, or a Redis-to-Valkey migration for one account; the broker separately verifies UID 0, resolves the account from trusted cPanel metadata, validates its manifest, maps actions to fixed manager methods, and records actor/account/action/result/state through syslog. Denied non-root attempts are logged with the kernel peer UID. Stop, restart, restore, migration, and recovery start require explicit browser confirmation, and the page reports transitional states such as `starting` or `stopping`.

## Dashboard and accounts

The installed fleet page reports the exact count of verified configured accounts across the inventory and state counts for the visible page only. Per-page counts distinguish running, stopped, starting, stopping, failed, and unverifiable instances. “Unverifiable” means the broker could not validate the manifest, ownership, or service state; it is not included as a fleet-wide service-state total. Account search and filters apply to the current page. Additional full-fleet live metrics and alerts remain planned work.

## Admin surfaces

- **Read-only Redis diagnostics:** for one running account, WHM invokes only `PING`, `INFO server`, `INFO memory`, `INFO clients`, `INFO stats`, and `DBSIZE` using the trusted manifest's Unix socket and installed client. The returned allowlist contains backend/version, uptime, memory, client counts, commands per second, database 0 key count, and keyspace/expiry/eviction counters. Raw command output, keys, values, and credentials never reach the UI or audit record. Each account is limited to one request per five seconds. There is no free-form Redis command console.
- **Backups:** support a selected account and optional fleet run with per-account results and retention visibility.
- **Recovery:** scan one selected account with a read-only manifest/service check and fixed `PING` health probe when running. A verified stopped or failed service may offer only the fixed `start` repair. The repair re-scans, obtains the per-instance operation lock, and checks the manifest and state again before starting; malformed or unowned manifests, timeouts, transitions, and failed probes never trigger an automatic repair. Scan and repair outcomes are recorded separately without raw output or Redis data.
- **Backend migration:** offer a Redis-to-Valkey operation only for a running ORM-managed Redis account. The accepted range is Redis 6.2 through 7.2 to Valkey 7.2 or newer. Redis OSS 7.4 and later is rejected because its RDB format is not compatible with the supported target range. The root administrator must first stop or pause every application writer and acknowledge that state in WHM. ORM pauses Redis writes, takes a root-controlled snapshot, validates that snapshot with the Valkey RDB checker, stops Redis, installs the snapshot, atomically updates the backend manifest, starts Valkey, checks `PING`, and compares database key and expiry counts. Failures after stopping Redis trigger an attempt to validate and restore the saved Redis snapshot and restart Redis. The snapshot remains available for manual recovery.
- **Backend settings:** show detected Redis/Valkey server and CLI tools, services, versions and managed counts. Readiness checks do not start a migration.
- **Provider settings:** configure report/warn/enforce, UI exposure, defaults, package ceilings and reseller quotas. Enforcement begins with new provisioning.
- **Security:** surface authentication, credential hygiene and resource use as actionable review items.
- **Branding:** preview the account-facing product name, logo, support URL and colors.
- **Updates:** show the source version and release information; preserve existing instances and data.
- **Audit:** filter operational events by time, actor, target and result; never include secrets.

## Authorization

The fleet view is root-only. The WHM application asks the local broker for its inventory; the broker checks the kernel-derived peer UID and accepts the fleet operation only from UID 0. It lists only ORM metadata backed by a matching cPanel account record and valid local account identity. Names and state are escaped before rendering; paths, configuration, credentials, and Redis data are omitted. Pagination keeps broker replies within the protocol size limit. Snapshot entries contain only validated IDs, timestamps, and sizes. Search, state filtering, and state counts apply to the displayed page.

Fleet controls, diagnostics, recovery, backup, and migration operations are root-only and use POST on a WHM `cpsess` route. The broker rejects non-root peers, malformed account names, unknown actions, untrusted account records, and invalid instance manifests before invoking a manager method. Diagnostics are rate-limited per account and use only the fixed read-only probes listed above. Their metrics are validated at the broker boundary; an unconfirmed audit write is shown separately from the result. Restart is limited to running or starting instances. Snapshot, recovery, and migration operations are rate-limited per account and cannot target arbitrary paths; restore requires a retained account-owned snapshot, performs the existing safety-snapshot and rollback flow, and can briefly interrupt the service or discard newer writes. Recovery accepts only the fixed `start` action, runs a fresh read-only manifest/state scan and `PING`, then rechecks the manifest and state while holding the per-instance lock. Migration requires the fixed Valkey target plus a positive application-writer quiescence acknowledgement; the broker also enforces a per-instance operation lock shared with lifecycle, configuration, backup, and restore actions. Migration checks server versions, snapshot validation, service health and database key/expiry counts, and attempts rollback to Redis on failure. These checks do not compare key contents and do not replace the requirement to keep application writers paused until the migration has been verified. Each request acts on one selected account and reports that account's result; the page does not run an all-fleet batch. Recovery events are written to the host's `authpriv` syslog; log rotation and retention follow the server's syslog policy. A free-form Redis CLI and per-account WHM configuration remain unimplemented. Refer to the [security model](../security-model.md).
