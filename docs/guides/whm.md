# WHM administrator guide

The installed WHM addon displays detected Redis and Valkey backends and the selected default for new instances. ORM-managed direct instances use validated host binaries and per-account systemd services. Separately, the cPanel account page can discover existing cPanel EA Podman Redis/Valkey sockets owned by that account and generate application connection settings; cPanel retains control of those container services and backups. Root WHM administrators also have a paginated view of ORM-managed account names, backend, normalized service state, and up to three retained snapshots per account, with per-page search and state filters. Root can request start, stop, restart, fixed read-only diagnostics, a fixed recovery scan, an on-demand fleet summary, one-account snapshot operations or a capped two-account backup/restore batch, or a Redis-to-Valkey migration for one account; the broker verifies UID 0, resolves account identities from trusted cPanel metadata, validates manifests, maps actions to fixed manager methods, and records individual outcomes through syslog. Denied non-root attempts are logged with the kernel peer UID. Stop, restart, restore, migration, and recovery start require explicit browser confirmation, and the page reports transitional states such as `starting` or `stopping`.

## Dashboard and accounts

The installed fleet page reports verified account inventory and visible-page state counts. A separate POST action loads a bounded summary: one batched systemd query for valid managed instances plus root-owned scheduled metric snapshots that are fresh for up to 15 minutes. Fresh metrics report aggregate memory and connected clients plus memory/client-pressure and low-hit-ratio alert counts. A separate root-owned counter snapshot reports per-account deltas for evicted keys and total processed commands only when consecutive samples are monotonic, uptime-continuous, and no more than 26 hours apart. When the backend exposes `acl_access_denied_auth`, it independently reports anonymous authentication-failure deltas under the same window and reset checks. It reports actual interval bounds and maximum per-account deltas without assigning an abuse threshold. Missing fields/baselines, resets, and longer gaps remain unknown. Stale, missing, unverified, unavailable, and unconfigured accounts are identified; stale and missing metrics are not counted as zero, and incomplete counter coverage marks the summary partial. The summary is on-demand and does not probe Redis or start a live metrics collection across the fleet.

## Admin surfaces

- **Read-only Redis diagnostics:** for one running account, WHM invokes only `PING`, `INFO server`, `INFO memory`, `INFO clients`, `INFO stats`, and `DBSIZE` using the trusted manifest's Unix socket and installed client. The returned allowlist contains backend/version, uptime, memory, client counts, commands per second, database 0 key count, and keyspace/expiry/eviction counters. Raw command output, keys, values, and credentials never reach the UI or audit record. Each account is limited to one request per five seconds. There is no free-form Redis command console.
- **Backups:** choose one or two running accounts on the visible page for a sequential create or restore batch. Each target is resolved again and gets an independent outcome; a failed account does not suppress the other result. Restore requires a retained snapshot selected for that same account and uses the existing safety snapshot and rollback flow. Batch operations are rate-limited and audited per account.
- **Recovery:** scan one selected account with a read-only manifest/service check and fixed `PING` health probe when running. A verified stopped or failed service may offer only the fixed `start` repair. The repair re-scans, obtains the per-instance operation lock, and checks the manifest and state again before starting; malformed or unowned manifests, timeouts, transitions, and failed probes never trigger an automatic repair. Scan and repair outcomes are recorded separately without raw output or Redis data.
- **Backend migration:** offer a Redis-to-Valkey operation only for a running ORM-managed Redis account. The accepted range is Redis 6.2 through 7.2 to Valkey 7.2 or newer. Redis OSS 7.4 and later is rejected because its RDB format is not compatible with the supported target range. The root administrator must first stop or pause every application writer and acknowledge that state in WHM. ORM pauses Redis writes, takes a root-controlled snapshot, validates that snapshot with the Valkey RDB checker, stops Redis, installs the snapshot, atomically updates the backend manifest, starts Valkey, checks `PING`, and compares database key and expiry counts. Failures after stopping Redis trigger an attempt to validate and restore the saved Redis snapshot and restart Redis. The snapshot remains available for manual recovery.
- **Backend settings:** show detected Redis/Valkey server and CLI tools, services, versions and managed counts. Readiness checks do not start a migration.
- **Provider settings:** configure report/warn/enforce, UI exposure, defaults, package ceilings and reseller quotas. Enforcement begins with new provisioning.
- **Security and abuse review:** root WHM can generate a report-only review at most once per minute. It uses fresh fleet memory/client/hit-ratio aggregates, verified per-account eviction and operation counter deltas, an optional backend authentication-failure counter, and the last 24 hours of normalized ORM AUTH management events. Root can set separate report-only thresholds for eviction deltas, average operations per second, and authentication-failure deltas. Thresholds default to disabled and only change report severity; automated enforcement is not implemented. Counter evidence shows actual sample intervals of up to 26 hours. Missing fields/baselines, resets, and partial sources stay unknown. Authentication counters are anonymous aggregates; they do not identify clients or distinguish mistakes from attacks. The report does not remediate services, inspect passwords, or evaluate credential strength/reuse. See the [security report threshold guide](security-report-thresholds.md).
- **Branding:** preview the account-facing product name, logo, support URL and colors.
- **Updates:** show the source version and release information; preserve existing instances and data.
- **Audit:** root WHM can search retained ORM audit events by UTC date range (up to seven days), account, action, and result, and download normalized JSON. Actor UID, account, fixed action/result/state, timestamp, and the ORM source identifier are shown. Source coverage reports unavailable, timed-out, truncated, or unrecognized rows. It does not show cPanel provisioning, configuration, start, or stop events; host journal retention controls how far back records exist.
- **Provider events:** root WHM can configure an optional signed HTTPS event destination, enable or disable delivery, rotate its secret, and inspect bounded queue status. Delivery is disabled by default and the key is never shown again after generation. Receivers must validate HMAC, timestamps, and duplicate IDs. See the [provider event guide](provider-events.md).

## Authorization

The fleet view is root-only. The WHM application asks the local broker for its inventory; the broker checks the kernel-derived peer UID and accepts the fleet operation only from UID 0. It lists only ORM metadata backed by a matching cPanel account record and valid local account identity. Names and state are escaped before rendering; paths, configuration, credentials, and Redis data are omitted. Pagination keeps broker replies within the protocol size limit. Snapshot entries contain only validated IDs, timestamps, and sizes. Search, state filtering, and state counts apply to the displayed page.

Fleet controls, diagnostics, recovery, backup batches, and migration operations are root-only and use POST on a WHM `cpsess` route. The broker rejects non-root peers, malformed account names, unknown actions, untrusted account records, and invalid instance manifests before invoking a manager method. Batch creation/restoration is limited to two accounts from the visible page; the broker caps work, applies global and per-account rate limits, isolates failures, and returns strict per-account results. Metrics are read from validated root-owned snapshot files, and service state uses fixed argv systemd requests. Snapshot and migration operations cannot target arbitrary paths; restore requires a retained account-owned snapshot, performs the safety-snapshot and rollback flow, and can interrupt a service or discard newer writes. The [security model](../security-model.md) describes the authorization and isolation boundaries.
The audit view reads only the fixed `orm-broker` and `orm-whm` identifiers from `authpriv`, and returns recognized event fields rather than raw journal messages. It intentionally cannot establish complete host activity: cPanel instance provisioning, configuration, start, and stop events are not currently recorded in these sources. No matching retained rows may mean that the journal has expired or forwarded the events elsewhere. Exports are private, no-store JSON and include source coverage and limitations.
