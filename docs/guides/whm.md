# WHM administrator guide

The installed WHM addon displays detected Redis and Valkey backends and the selected default for new instances. Root WHM administrators also have a paginated view of ORM-managed account names, backend, normalized service state, and up to three retained snapshots per account, with per-page search and state filters. Root can request start, stop, restart, snapshot creation, restoration of a selected snapshot, or a Redis-to-Valkey migration for one account; the broker separately verifies UID 0, resolves the account from trusted cPanel metadata, validates its manifest, maps actions to fixed manager methods, and records actor/account/action/result/state through syslog. Denied non-root attempts are logged with the kernel peer UID. Stop, restart, restore, and migration require explicit browser confirmation, and the page reports transitional states such as `starting` or `stopping`.

## Dashboard and accounts

Show managed/running/stopped instances, aggregate memory and connections, backend health and recent alerts. Account search and filters should expose per-account status, port, memory, clients and health. Actions must target one selected account and report a structured result.

## Admin surfaces

- **Redis CLI:** default to a small set of read-only diagnostics. Never pass arbitrary submitted text to a shell. Apply explicit ACL checks and audit command classes.
- **Backups:** support a selected account and optional fleet run with per-account results and retention visibility.
- **Recovery:** scan first; list affected accounts; let the admin repair only selected accounts; audit every change.
- **Backend migration:** offer a Redis-to-Valkey operation only for a running ORM-managed Redis account. The accepted range is Redis 6.2 through 7.2 to Valkey 7.2 or newer. Redis OSS 7.4 and later is rejected because its RDB format is not compatible with the supported target range. The root administrator must first stop or pause every application writer and acknowledge that state in WHM. ORM pauses Redis writes, takes a root-controlled snapshot, validates that snapshot with the Valkey RDB checker, stops Redis, installs the snapshot, atomically updates the backend manifest, starts Valkey, checks `PING`, and compares database key and expiry counts. Failures after stopping Redis trigger an attempt to validate and restore the saved Redis snapshot and restart Redis. The snapshot remains available for manual recovery.
- **Backend settings:** show detected Redis/Valkey server and CLI tools, services, versions and managed counts. Readiness checks do not start a migration.
- **Provider settings:** configure report/warn/enforce, UI exposure, defaults, package ceilings and reseller quotas. Enforcement begins with new provisioning.
- **Security:** surface authentication, credential hygiene and resource use as actionable review items.
- **Branding:** preview the account-facing product name, logo, support URL and colors.
- **Updates:** show the source version and release information; preserve existing instances and data.
- **Audit:** filter operational events by time, actor, target and result; never include secrets.

## Authorization

The fleet view is root-only. The WHM application asks the local broker for its inventory; the broker checks the kernel-derived peer UID and accepts the fleet operation only from UID 0. It lists only ORM metadata backed by a matching cPanel account record and valid local account identity. Names and state are escaped before rendering; paths, configuration, credentials, and Redis data are omitted. Pagination keeps broker replies within the protocol size limit. Snapshot entries contain only validated IDs, timestamps, and sizes. Search and state filtering apply to the displayed page.

Fleet controls, backup, and migration operations are root-only and use POST on a WHM `cpsess` route. The broker rejects non-root peers, malformed account names, unknown actions, untrusted account records, and invalid instance manifests before invoking a manager method. Restart is limited to running or starting instances. Snapshot and migration operations are rate-limited per account and cannot target arbitrary paths; restore requires a retained account-owned snapshot, performs the existing safety-snapshot and rollback flow, and can briefly interrupt the service or discard newer writes. Migration requires the fixed Valkey target plus a positive application-writer quiescence acknowledgement; the broker also enforces a per-instance operation lock shared with lifecycle, configuration, backup, and restore actions. Migration checks server versions, snapshot validation, service health and database key/expiry counts, and attempts rollback to Redis on failure. These checks do not compare key contents and do not replace the requirement to keep application writers paused until the migration has been verified. A missing audit-write confirmation is shown separately from the operation result. Each request acts on one selected account and reports that account's result; the page does not run an all-fleet batch. The Redis CLI, repair, and per-account WHM configuration are still unimplemented. Refer to the [security model](../security-model.md).
