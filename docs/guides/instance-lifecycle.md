# Account instance lifecycle

## Current behavior

The installed cPanel page supports inspect state, read live metrics, initialize, configure bounded settings, start, and stop for the signed-in account. WHM must first select an installed Redis or Valkey server as the default backend for new ORM instances. The backend choice is stored in a root-owned policy file and does not change existing services.

Each browser request is cross-checked against the local broker. The broker derives the target account from the kernel-supplied Unix peer UID and the trusted cPanel account record. Requests contain no username, path, unit, command, port, or arbitrary configuration values. Initial provisioning may carry only one of five fixed preset IDs; configuration requests carry four typed, bounded fields from a fixed schema. The client sends one newline-terminated frame and closes its write side before dispatch. Mutating requests are rate-limited.

On initialization, ORM creates a per-account service using `orm-instance@<account>.service`. The service runs under that cPanel account and uses a private Unix socket inside the account's mode-0700 data directory. Redis/Valkey TCP access is disabled. The selected cPanel preset provides a baseline of 32, 48, or 64 MiB; the provider's 8–64 MiB default can lower that value, and the package memory ceiling still gates provisioning. WHM also selects the allowlisted eviction policy and 1–16 logical databases for new instances. All profiles use 100 clients and no automatic RDB or AOF persistence. Existing user-editable settings can be changed within fixed bounds: 8–64 MiB, an allowlisted eviction policy, 10–100 clients, and a 0–300 second idle timeout. Running services receive fixed per-setting `CONFIG SET` calls without restart; the broker then atomically saves its generated config. Stopped or failed services save changes for the next start. Reducing memory can immediately evict keys. The systemd unit applies separate process memory, CPU, task and file-descriptor limits. The root-owned manifest records the initial preset and provider database/history defaults; older version 1 manifests are treated as Generic and retain their historical configuration.

For every configured instance, the page requests a read-only metric sample through the local broker. The broker derives the account and socket from peer credentials and its root-owned manifest, runs the fixed backend CLI with an argument vector, and returns only numeric used/peak memory, connected clients, uptime, operations per second, and keyspace hits/misses, plus a capture time, stale flag, and whether the live sample was retained. The command has a three-second deadline and bounded output; no command names, keys, credentials, or raw INFO text reach the browser. The broker atomically retains the latest successful sample as root-owned mode `0600` metadata next to the account manifest. If the service is stopped or the live probe fails, a valid sample no older than 30 days is returned with a stale marker. Invalid or expired snapshots are never displayed. If writing a fresh snapshot fails, the live values are still returned and the page says they could not be saved for fallback.

Each instance's systemd lifecycle starts a separate hourly metrics timer, which is bound to the instance and runs its fixed collector as that cPanel account. The collector uses only the local Unix socket. The root broker validates and stores one sample per hour in an atomic, root-owned `0600` history file. New instances use their manifest-recorded provider retention of 7–90 days, with a hard cap of 2,160 samples and 1 MiB; legacy instances retain 30-day pruning. The cPanel charts offer 24-hour and 7-day ranges for memory used, connected clients, and hit ratio. A live page request also refreshes the latest sample; within the same hour it updates that hour's history point. History is account-scoped and contains only numeric counters and timestamps.

## Security and preservation

- Instance identity and paths come from the broker's `SO_PEERCRED` account mapping; form fields cannot select another account.
- The WHM backend policy and instance manifests are root-owned. Configuration is root-owned and readable by the account group; only the account owns and can access its data directory.
- The launcher accepts only fixed Redis and Valkey binary paths and passes the fixed configuration path as an argument vector without a shell.
- The service uses only `AF_UNIX`, `PrivateNetwork`, strict filesystem protection, and one account-specific writable path.
- Opening the cPanel page only reads status. Start/stop and WHM policy changes are POST-only, require a `cpsess`-tokenized route, and rely on cPanel/cpsrvd to validate the session token.
- Uninstall refuses to remove ORM while entries remain under either managed instance root. It does not delete account data.

## Not implemented yet

The cPanel page displays the account's Unix socket endpoint, AUTH state, and the provider-selected feature tier. Simple shows status, setup, lifecycle, and the PhpRedis connection helper. Developer adds the five workload presets, live/history metrics, bounded configuration, all application helpers, and diagnostics. Advanced adds explicit RDB snapshots and restore; restore validates the snapshot and creates a safety copy before replacement, then verifies startup and attempts rollback on failure. AUTH is disabled by default. For a running instance, the account owner can enable or rotate its password; ORM restarts the service, verifies PING, and only then returns the generated password once. The owner can disable AUTH; ORM restarts and verifies passwordless PING before confirming. Failed verification attempts to restore the previous config and service. These actions briefly interrupt cache access; rotation revokes the previous password, while disable requires applications to remove their configured password. ORM does not expose TCP; the account-private socket remains the transport. Same-account applications can read the account's own configuration and use the password, so AUTH does not isolate mutually untrusted code running as that account. The account owns its Redis process and can change runtime values through that socket, so broker-saved settings are not protection against direct socket changes. Root WHM package policy can restrict new provisioning and broker-accepted memory changes; reseller quotas cap only new provisioning based on configured instances and aggregate memory, including stopped instances. Policy changes do not rewrite existing instances. Package retention is enforced after a newly created snapshot is validated and remains between two and three items. The tier changes visibility only; broker authorization remains account-scoped.
