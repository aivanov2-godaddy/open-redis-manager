# Provider event delivery design

Status: implemented in the repository for issue #143. The delivery integration still requires source-matched disposable-host validation before production use.

## Boundaries

Provider delivery is disabled by default and remains outside the Redis/Valkey request path. The privileged broker may append fixed events to a root-owned local outbox, but it has no network access. A separate root-only worker is the only component allowed to resolve or contact destinations. Enqueue failure is reported as telemetry failure and must never undo an already completed cache operation.

WHM owns event configuration. Store it separately from the general provider policy in a root-owned mode-0600 file. The destination is an HTTPS URL on port 443. The signing key is generated by ORM and rotated by replacement. Reads, broker responses, diagnostics, audit exports, event bodies, and the WHM page return no key or key fingerprint.

## Event contract

Schema version 1 uses a fixed catalog: `backend.selected`, `policy.denied`, `quota.reached`, and `instance.provisioned`, `instance.started`, `instance.stopped`, `instance.restarted`, and `instance.failed`. An envelope contains only `schema_version`, random `event_id`, UTC `occurred_at`, fixed `event_type`, and bounded allowlisted metadata. It contains no account identifier. No free-form input, command text, credentials, keys, values, connection strings, response bodies, or filesystem paths are allowed.

Serialize the envelope as UTF-8 canonical JSON with lexicographically sorted object keys and no insignificant whitespace. Sign the exact bytes with HMAC-SHA-256. Send the schema version, event ID, timestamp, and signature in fixed headers. Delivery is at-least-once: receivers must validate the signature and timestamp window and deduplicate event IDs. ORM cannot guarantee receiver-side replay rejection.

## Queue and delivery

The outbox is a root-owned directory and bounded atomic JSON records. Enqueue uses an exclusive lock, rejects duplicate IDs, and enforces limits of 256 records, 1 MiB total, 16 KiB per envelope, and 24-hour maximum age. The worker holds a separate nonblocking lock while selecting work. Each record tracks attempt count, next-attempt time, expiry, and a fixed state. Retry delays use capped exponential backoff with bounded jitter, no more than eight attempts; terminal failures are retained for operator inspection for 24 hours and then removed. Status UI reveals counts, ages, and normalized outcomes only.

Network delivery uses a dedicated systemd unit with network access; the broker retains `PrivateNetwork=true`. Resolve all A and AAAA answers for every attempt and reject the destination if any answer is non-global, special-use, or malformed. Connect to one validated address pinned for that request while keeping the original hostname for TLS SNI and certificate verification. Disable proxies and redirects, allow only TLS 1.2 or newer, and bound DNS/connect/total time, request bytes, response bytes, and response parsing. Never follow a redirect, even to another HTTPS URL.

## Audit, controls, and failure behavior

Root WHM can validate a candidate, enable or disable delivery, and rotate the secret. Validation performs no test POST. Configuration changes and normalized delivery outcomes use fixed `orm-whm` audit actions and contain no URL path, key, payload, or response body. A queue or network failure cannot block or roll back provisioning, lifecycle, configuration, or policy decisions.

## Required verification before enabling the feature

Tests must cover canonical bytes and signatures, timestamp bounds, duplicate IDs, queue caps and concurrent enqueue, crash-safe state updates, retry/expiry transitions, destination parsing, mixed public/private DNS answers, DNS pinning, IPv4/IPv6 special ranges, proxy suppression, redirect rejection, TLS hostname mismatch, timeouts, oversized responses, redaction, and a slow or failing endpoint proving the Redis operation returns independently. Packaging must install the disabled-by-default configuration, worker, and isolated unit. A source-matched disposable-host record is required before production-readiness claims.

Operator configuration, payload metadata, receiver checks, key rotation, disabling, and current validation limits are documented in [Provider event delivery](../guides/provider-events.md).
