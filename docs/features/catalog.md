# Feature catalog

This catalog records the public product behavior observed on the reference site and separates it from what this repository currently implements. Descriptions are summarized in our own words. Source pages and observation limits are in [source notes](../source-notes.md). Read implementation claims together with the [unreleased release notes](../release-notes.md): implemented behavior can remain experimental until host validation passes.

## cPanel account experience

| Feature | Expected behavior | Current implementation |
|---|---|---|
| Status and lifecycle | Show online, stopped, degraded or unavailable state; initialize, start and stop only the current account instance. | Authenticated cPanel entry point supports backend-gated initialize, status, start and stop through the peer-credential broker, with live metrics and stale fallback. Automated broker and page tests exist. Live cPanel behavior remains unverified. Uses an account-private Unix socket. |
| Connection details | Show the active endpoint, database and authentication mode; reveal or copy a secret only on explicit request. | The installed cPanel page shows ORM's private socket for an initialized direct-service instance, with copyable PhpRedis, WordPress/WooCommerce, LiteSpeed Cache, Laravel, Magento/Adobe Commerce, node-redis and redis-py helpers. It also detects current-account cPanel EA Podman Redis/Valkey sockets and performs a bounded read-only PING: PhpRedis supplies the parsed server version when installed; otherwise a fixed RESP PING verifies reachability without exposing commands or cache data. Podman caches remain managed by cPanel; ORM does not alter their containers or data. AUTH is off by default for ORM instances. Helpers use environment or paste placeholders and never contain secrets or edit application files. ORM-managed direct instances do not expose TCP. |
| Deployment modes and first-run setup | Choose an ORM-managed native Redis/Valkey service or an account-owned cPanel EA Podman container, with missing prerequisites and supported install steps explained. | The authenticated cPanel first-run wizard checks standard native binary locations, preserves WHM's root-owned native backend selection, and checks a verified account-owned EA Podman inventory plus its fixed package list. It offers only cPanel Redis 6.2/Valkey 7.2 install commands in the account's own Terminal/SSH context; it never runs a host package manager, arbitrary image/package/command, or cross-account container action. Missing tool, unsupported host/shell, timeout, unknown inventory, and verified absence remain distinct. cPanel retains container package and data ownership. A root-owned scheduled sampler provides anonymous WHM aggregate coverage for these sockets; it does not manage their package configuration or data. The one-shot collector passed a live cPanel check for an existing Redis and temporary Valkey socket (2 discovered, sampled, and reachable); the recurring timer remains disabled and the result does not establish a supported host matrix. See the [EA Podman sampler record](../validation/records/2026-11-21-cpanel-ea-podman-metrics-sampler.md). |
| Health and preflight | Explain whether an instance exists, is running and has authentication configured; link each warning to a remedy. | The installed cPanel page shows setup checks for initialization, service state and connection-detail availability plus the configured AUTH state when the broker responds. It calculates a transparent advisory score from the running state and current memory, client, and sufficiently sampled hit-ratio checks; unknown checks are excluded and shown in the coverage count. Stale/unavailable samples and non-running states have no numeric score. Application connection and client-extension availability remain unverified and unscored. |
| Metrics | Present memory, peak memory, connected clients, uptime, command rate and hit/miss ratio with a selectable time window. Mark stale samples. | The installed cPanel page shows bounded live/latest-known values plus hourly memory, client and hit-ratio charts with 24-hour and 7-day ranges. A per-account systemd timer collects only while the cache is running. New instances use their recorded 7–90 day provider retention; history remains root-owned `0600`, capped at 2,160 samples and 1 MiB. Legacy instances retain 30-day behavior; disposable-host validation remains open. |
| Presets | Offer WordPress, Laravel, Magento, session cache and generic starting profiles. Validate every saved setting against provider ceilings. | Developer and Advanced exposure offer five fixed presets with server-defined memory values capped at 64 MiB. Simple exposure initializes the Generic profile. Package and reseller quotas are checked by the broker when provisioning. |
| Advanced settings | Configure memory ceiling, eviction policy, database count, timeout, clients and persistence when provider exposure allows it. | Developer and Advanced exposure show memory (8–64 MiB), allowlisted eviction policy, clients (10–100), and idle timeout (0–300 seconds) through the account-bound broker. Database count and persistence remain host-controlled. Package memory ceilings are broker-enforced in enforce mode. |
| Backups and restore | Create account-scoped backups, list retained snapshots, and take a safety snapshot before replacing current data during restore. | The installed cPanel page creates, lists, downloads, and restores explicit RDB snapshots for the authenticated ORM-managed account. Root WHM can view retained snapshot metadata and request one-account actions or a capped two-account batch with ordered, independent outcomes and audit events. Restore accepts only an account-owned listed ID, validates its RDB, creates a safety snapshot, stops and restarts the service, verifies the active state, and attempts rollback if startup fails. Snapshots are root-controlled, capped at 128 MiB and 60 seconds, and retained to the newest three. cPanel Podman containers remain under cPanel's own backup/lifecycle controls. |
| Application detection | Detect common app markers without reading secrets or changing files; show an integration status that the user can correct. | The installed page can on demand scan up to 32 authenticated cPanel domain roots for fixed WordPress, Laravel, Drupal, Joomla, Magento/Adobe Commerce and Symfony marker sets. It checks metadata only, returns fixed app names without domain/path details, and calls every connection status unverified. It rejects observed symlink components and runs only as the matching cPanel account; path-based checks cannot eliminate a concurrent rename/symlink race. Unsupported execution identity or API/root failures fail closed. Live cPanel and CageFS behavior still requires disposable-host validation. |
| Connection helper | Render examples for WordPress, LiteSpeed Cache, Laravel, Magento, plain PHP, Node.js and Python. Mask secrets in generated diagnostics. | The installed cPanel page generates account-specific Unix-socket examples for those application clients, including version-neutral Magento connection values and a link to its release-specific guide. WooCommerce uses the WordPress object-cache path. The helpers do not modify application files. |
| Diagnostics export | Preview and download a support report with bounded configuration and health context while redacting credentials and private values. | The authenticated cPanel page previews and downloads an in-memory JSON report with allowlisted state, bounded settings and metrics. It excludes account names, hostnames, paths, credentials, Redis keys/values, application payloads/sessions, logs and raw command output; exports are not retained. |
| Health guidance | Summarize the state with actionable suggestions for memory pressure, weak cache hit ratio, connection issues and disabled runtime clients. | The authenticated cPanel page gives advisory guidance for stopped/failed state and current metrics: memory at 85% or more of the configured ceiling, clients at 85% or more of the configured limit, and a cumulative hit ratio below 50% after at least 100 lookups. Its four-check score is available only with at least three verifiable checks and a fresh sample; the page shows evidence coverage and never treats unknown checks as passes. It labels the hit ratio as cumulative since process start and does not verify application connectivity, runtime extensions, or guarantee cache performance. Thresholds and score are heuristics. See the [health guidance notes](../guides/health-guidance.md). |
| Safe live configuration | Apply an account-level memory change live where supported; preserve account ownership and report apply failures instead of implying the saved file took effect. | Developer and Advanced exposure allow bounded memory, eviction policy, client count and idle-timeout changes through the account-bound broker. For a running service, ORM reads current runtime settings, applies the allowlisted values, then atomically saves the generated config; it attempts to restore captured runtime values if apply or save fails. Stopped instances save values for their next start. Database count, persistence and arbitrary directives are not editable. |
| Authenticated account context | Derive the current account from the cPanel session and use it for all account-scoped reads and writes. | The cPanel page cross-checks the LiveAPI username with the peer-credential broker, and lifecycle operations use that broker-derived account. A single-host identity smoke passed; lifecycle operations and the supported host matrix still need cPanel validation. |

## WHM server administration

| Feature | Expected behavior | Current implementation |
|---|---|---|
| Fleet dashboard | Summarize managed/running accounts, connections, memory, backend availability and service health. | The installed WHM page shows a root-only paginated inventory and on-demand fleet summary. The broker validates account identity and manifests, makes one bounded systemd state query, and aggregates only root-owned scheduled metrics snapshots no older than 15 minutes. The UI identifies fresh, stale, missing, unverified and unconfigured accounts; stale/missing values are excluded from totals and make the response partial. Alerts summarize memory/client pressure and weak hit ratio. |
| Account manager | Search and filter accounts by state; inspect usage; start, stop, restart and edit within package limits. | Root can start, stop and restart a selected validated instance. Each row shows memory and connected-client usage against the validated instance limits, using only the root-owned metrics snapshot and the existing 15-minute freshness window; stale, missing, invalid, or future-dated measurements remain labelled stale or unknown and are never shown as zero. Search and state filters apply to the current page. Package policy enforcement is documented under [Package limits](#package-limits); per-row package-cap context remains unavailable. |
| Backend discovery | Detect Redis and Valkey service, server/CLI binary, version and managed account counts. Explain selection and migration readiness. | WHM displays read-only discovery and lets root WHM select the installed default for future ORM instances. Root can load aggregate Redis/Valkey counts from the verified fleet summary; older brokers may not provide them. Migration readiness remains unavailable. |
| Redis command console | Run an allowlisted set of read-only diagnostics against a chosen account; any administrator console must be separately permissioned and audited. | Root WHM selects one fixed class per request: `PING`, `INFO server`, `INFO memory`, `INFO clients`, `INFO stats`, or `DBSIZE`. The broker resolves the trusted account/socket, invokes only the selected fixed arguments, validates its exact typed fields, records root actor/account/command-class/outcome, and rate-limits each account to one request every five seconds. The UI renders normalized fields only; it never returns arbitrary command output, keys, values, or credentials. Free-form Redis commands and arbitrary INFO sections remain unsupported. |
| Backups | Browse account snapshots and request targeted or fleet backups; report partial failures per account. | WHM lists up to three retained snapshots for each displayed account, supports individual actions, and offers batches for one or two running accounts from the current page. Each account is resolved again and processed sequentially; per-account rate limits, restore safety snapshots, rollback, audit records, and partial outcomes remain separate. |
| Recovery | Scan first, repair only affected accounts, rebuild configuration from trusted metadata, fix ownership, rotate credentials, and audit each action. | Root WHM can run a read-only scan for one selected account and offer fixed `start` or `config_rebuild` repairs. Config rebuild is limited to a stopped/failed instance with an intact root-owned manifest and safely readable config whose bounded settings and AUTH directive validate; it atomically removes unrecognized additions, verifies the canonical result, and does not start the service. Missing or malformed core config, ownership repair, and WHM-directed credential rotation are not implemented; account owners can enable or rotate AUTH from cPanel. Live cPanel validation remains open. |
| Provider policy | Choose report-only, warn or enforce; select Simple, Developer or Advanced exposure; keep grandfathering explicit. | Root WHM manages package enablement, memory/client/database and snapshot-retention ceilings, reseller instance and aggregate-memory quotas, global exposure, and defaults for new instances. Report-only logs, warn allows with fixed cPanel notices, and enforce blocks applicable new provisioning or over-cap memory/client increases. An existing client value above a lowered cap can remain unchanged or decrease. Policy changes do not rewrite existing configuration. |
| Global defaults | Set memory, eviction, database, backup and history defaults for newly provisioned accounts. | Root WHM configures 8–64 MiB memory, an allowlisted Redis/Valkey eviction policy, 1–16 databases, default snapshot retention through package rules, and 7–90 day metrics-history retention. New manifests record effective snapshot-retention, database, and history defaults; memory remains bounded by the selected preset and package ceiling, while client and database settings are capped by package policy. Updating defaults does not rewrite existing instance configuration or history. The Redis/Valkey backend selector applies to future ORM instances. |
| Package limits | Set eligibility, memory/client/database ceilings and backup retention per package. | Root WHM can enable or disable new provisioning per package, set memory ceilings (8–64 MiB), snapshot retention (two or three), client limits (10–100), and database limits (1–16). New instances receive the lower of the generated/global value and the package ceiling. Later over-cap client increases follow the provider mode; existing higher settings can remain unchanged or be reduced. Automatic provisioning remains unimplemented. |
| Reseller quotas | Summarize managed accounts, active instances and memory; cap new instances and aggregate memory without mutating existing services. | Root WHM shows configured instances, active instances and configured memory per trusted account OWNER. Stopped instances count toward quota checks. A zero limit means unlimited. |
| Security | Surface authentication failures, credential hygiene and resource-abuse signals; rotate credentials with rollback-safe sequencing. | Root WHM generates a rate-limited, report-only review from fresh fleet memory/client/hit-ratio aggregates, bounded eviction and processed-command counter deltas, an optional backend `acl_access_denied_auth` counter, and normalized ORM AUTH management events. Counter rates require monotonic samples, uptime continuity, and intervals no longer than 26 hours. The optional auth counter is detected at runtime; missing fields/baselines and resets remain unknown. Findings use anonymous aggregate deltas and do not identify clients or establish attacks. ORM does not inspect passwords. It logs only a fixed metadata event. Optional account-level Redis AUTH remains account-controlled and its generated secret is shown once after verification. |
| Abuse reports | Score supported resource and authentication signals and present bounded evidence for administrator review. Abuse findings are report-only; provider policy's report/warn/enforce modes are separate provisioning controls. | Partial: report-only memory pressure (85%), client pressure (85%), cumulative hit ratio (<50% after 100 lookups), and optional configurable report-only thresholds for eviction deltas, average operations per second, and authentication-failure deltas. Thresholds default to disabled, are stored separately in a root-owned policy, and change report severity only. Each report is rate-limited to one per minute and marks partial/unavailable sources unknown. Findings show UTC evidence-window bounds, sample times where available, and review recommendations; counter evidence includes actual sample intervals up to 26 hours. A separate EA Podman coverage finding uses the root-owned scheduled aggregate snapshot; Podman counter-rate deltas and thresholds are not implemented. Automated enforcement for abuse signals is not implemented; no credentials, Redis keys, or client identities are inspected. A live ORM-managed Valkey 7.2.15 instance contributed bounded counters to the WHM report engine, and the authenticated WHM response rendered the eviction, operation, and optional authentication findings in report-only mode on one cPanel host. The same cPanel host also exercised the root-owned Podman sampler against its existing Redis and temporary Valkey sockets (2 discovered, sampled, and reachable). This verifies anonymous aggregate coverage collection on one host; it does not add Podman counter-rate abuse findings or validate the broader support matrix. See the [EA Podman sampler record](../validation/records/2026-11-21-cpanel-ea-podman-metrics-sampler.md). Browser visual review remains open. See also the [WHM report threshold guide](../guides/security-report-thresholds.md), [Valkey live report record](../validation/records/2026-11-21-valkey-security-report-live.md), [report form record](../validation/records/2026-11-21-whm-security-report-live.md), and [Valkey field probe](../validation/records/2026-11-21-valkey-security-counter-probe.md). |
| Authentication protection | Rate-limit repeated authentication failures, audit lockouts without logging secrets, and detect weak or reused credentials without exposing values. | The report measures anonymous backend auth-failure counter deltas only when the backend exposes the INFO field; unsupported versions and incomplete windows remain unknown. It does not identify clients, create lockouts, or evaluate credential strength/reuse. Broker operations use Unix-socket peer credentials and fixed request rate limits. Redis AUTH is optional and is not a substitute for account isolation. |
| Branding | Configure provider product name, logo, support link, four labelled theme colors, brand-inspired palettes, footer visibility and a live cPanel preview. | Root WHM stores validated provider branding in the root-owned v4 policy file. The account-scoped broker exposes only display data to cPanel. The four palette roles are primary action, link, panel background, and text; the project-authored ORM, UnderHost-inspired, Redis-inspired, and Valkey-inspired palettes change colors only. |
| Updates | Verify release metadata and expose an administrator-approved update path that preserves existing accounts. | Root WHM verifies a manually staged, locally signed release against the installed v3 manifest, displays signature, digest and per-file actions, and requires a fresh conflict-free preview plus explicit confirmation. A fixed worker applies the bound version and artifact asynchronously through the transactional updater and exposes bounded status and recovery states. Releases are not fetched automatically; existing v1/v2 installs need exact-match manifest adoption, and the workflow still needs live cPanel validation. See the [update lifecycle guide](../guides/update-lifecycle.md). |
| Audit | Record privileged changes and operation results without secrets; support filtering and export. | Root WHM can search retained, recognized `orm-broker` and `orm-whm` authpriv events by UTC range (up to seven days), account, fixed action, and result, then export normalized JSON. Missing, truncated, or unrecognized journal rows are shown as incomplete coverage. cPanel provisioning, configuration, start, and stop events are not included, and host retention controls availability. |
| Backend migration | Snapshot, switch one account, verify health and connectivity, then roll back on failure. Require explicit confirmation and show downtime/data semantics. | Root-only WHM migration is wired for a running ORM-managed Redis 6.2–7.2 instance to Valkey 7.2 or newer. It requires an explicit acknowledgement that application writers have already been stopped or paused, briefly pauses Redis writes, saves and validates an RDB snapshot, switches the backend, checks service health and per-database key/expiry counts, and attempts automatic rollback on failure. It rejects unsupported versions and keeps a safety snapshot. Exact key values are not compared; maintain the application write pause through verification and resume it only after success. Disposable cPanel migration testing remains an open release gate. |
| Update lifecycle | Show signed release state in WHM, preserve existing account configuration and data, and provide an explicit post-update status and recovery path. | WHM now provides signed release preview, explicit apply confirmation, asynchronous transaction jobs, and bounded status/recovery reporting. The worker refuses unsupported file actions and binds the confirmed version and digest. Releases must be staged and signed out of band; the older identity-v1 bridge remains a separate compatibility path, and live cPanel install/update validation is open. |
