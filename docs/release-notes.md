# Unreleased development notes

- WHM recovery can scan the bounded ORM account data tree and restore account ownership and private modes for directories, single-link regular files, and the canonical Redis socket while the service is stopped or failed. It preserves file bytes and refuses symlinks, hard links, other special files, unexpected owners/groups, cross-device paths, and resource-limit overflow. Live cPanel validation remains open.

- EA Podman WHM reporting now computes report-only maximum per-process eviction, operation, and optional authentication-failure deltas after complete scans confirm the exact same Redis/Valkey server-ID set and monotonic counters. A separate root-only baseline stores SHA-256 server-ID digests and allowlisted counters; digests are linkable pseudonymous state and never leave that file. Process changes, resets, partial scans, invalid state, and gaps beyond 26 hours remain explicitly unknown.
- WHM recovery can now reset a safely owned missing or malformed managed config from a trusted manifest. The repair uses an 8 MiB / 10-client profile, creates a new AUTH password shown once in a private no-store response, preserves Redis data, and leaves the service stopped; unsafe ownership, modes, symlinks, or account paths still block repair.
- The idempotent installer verifies the cPanel account-create hook using the action-suffixed script path returned by `manage_hooks list`.
- The per-account systemd unit now retries unexpected failures after 10 seconds and caps starts at five per five-minute window, preventing an indefinite rapid restart loop. Operators can inspect the unit journal, resolve the cause, and clear the failed start counter before retrying.
- Both installed cPanel and WHM entry points reject POST requests without a valid-format `cpsess` route before platform API initialization or submitted-field processing. Authenticated SSO confirmed rejection of missing-token POSTs and a valid-token WHM policy round trip on one cPanel & WHM 138.0 build 27 test host; cPanel `cpsrvd` remains responsible for validating the token itself. Other mutations and host coverage remain open. See the [sanitized session-token record](validation/records/2026-11-21-cpanel-whm-session-token-csrf.md) and [WHM policy round-trip record](validation/records/2026-11-22-whm-valid-session-policy-roundtrip-live.md).
- WHM signed-update previews now identify broker and systemd changes that need maintenance, check the broker before queueing, and refuse active or unverifiable states without changing service state. The transactional updater retains its final guard against service-state races.

**Updated:** 2026-11-22
**Release:** `0.1.0-rc.14` is a source-matched validation candidate. The signed updater preview and guarded maintenance apply passed on one disposable cPanel host; eight fixed WHM diagnostics, including `SLOWLOG` and `INFO commandstats`, passed with per-class audit events. No public release is published and milestone 0.1.0 release gates remain open. See the [sanitized live validation record](validation/records/2026-11-22-whm-diagnostics-slowlog-live.md).

The cPanel instance launcher now validates the current version-three instance manifest as well as the retained version-one and version-two formats. This allows newly provisioned Redis and Valkey services to start with the manifest schema written by the broker.

These notes distinguish repository implementation from deployment readiness. A feature can exist in the code while remaining experimental for cPanel deployments.

## Status meanings

- **Implemented:** the documented behavior exists in the repository. This label alone does not establish production readiness.
- **Experimental:** a working implementation exists, but its end-to-end behavior or supported host matrix has not passed the disposable cPanel release gate.
- **Planned:** the behavior is not implemented in the repository.

## Implemented

- WHM security reports now support separate root-owned, report-only thresholds for eviction deltas, average operations per second, and optional authentication-failure deltas. All thresholds default to disabled; a threshold only changes finding severity. Automated enforcement remains unimplemented. See the [threshold guide](guides/security-report-thresholds.md).

- cPanel setup preflight now reports whether PhpRedis is loaded in the PHP runtime serving the ORM page, with a version when available. It warns that domain PHP handlers may differ, suggests enabling the extension only for PHP applications that need it, and does not claim application connectivity. See [issue #203](https://github.com/aivanov2-godaddy/open-redis-manager/issues/203) and the refreshed [application preflight screenshot](../screenshots/cpanel-application-discovery.png).

- The authenticated cPanel first-run wizard offers native Redis/Valkey or cPanel EA Podman, reports missing or partial native server/CLI installations, and guides account owners through provider-approved setup and recheck steps. The WHM package policy can separately opt new accounts into Generic ORM-managed provisioning; that post-create hook is best-effort and disabled by default for every package. Disposable cPanel validation of new account creation remains open. See the [first-run setup guide](guides/cpanel-first-run-setup.md) and [provider package policy guide](guides/provider-package-policy.md).

- WHM audit history now includes metadata-only ORM-managed cPanel provisioning, configuration, start, and stop requests. The event records the broker peer UID, resolved account, fixed action, success/failure, and normalized state; it excludes submitted settings, secrets, and raw errors. EA Podman commands remain outside this audit stream. See [issue #205](https://github.com/aivanov2-godaddy/open-redis-manager/issues/205) and the refreshed [audit log screenshot](../screenshots/whm-audit-log.png).

- Standalone sample-data PHP prototype for reviewing layout and workflows; it does not connect to Redis.
- Application guides and copyable connection examples; ORM does not edit application files or establish client compatibility for a specific host.
- Broker-backed Redis/Valkey per-account provisioning, status, bounded configuration, lifecycle controls, metrics, and hourly history.
- Account backups, restore with safety snapshot and rollback attempt, Redis-to-Valkey migration, selectable root-only WHM read-only diagnostics for PING, INFO server/memory/clients/stats, and DBSIZE, provider policy controls, and guarded recovery scan/start/config-rebuild/config-reset. Config rebuild preserves validated bounded settings and AUTH; reset uses a fixed low-resource profile and replacement AUTH while preserving data and leaving the service stopped. Both verify canonical output and refuse untrusted paths. See the [recovery guide](guides/whm.md).
- Advisory cPanel health guidance and a four-check health score for verified service state, memory/client pressure, and sufficiently sampled hit ratio. The score shows its evidence coverage, excludes unknown checks, and is withheld when fewer than three checks or fresh metrics are available. It does not verify application connectivity or guarantee performance.
- Root-only WHM audit search and normalized JSON export for retained ORM broker and WHM policy events, with bounded journal reads and visible source coverage gaps.
- Account-scoped discovery of existing cPanel EA Podman Redis/Valkey containers, fixed bounded RESP PING/INFO probes, allowlisted ephemeral memory/client/uptime/operations/hit metrics, safe version reporting, application connection examples, and fixed start/stop/restart controls that call cPanel's EA Podman tool as the owning account. Metrics are not retained; keys and values are never requested. cPanel retains package configuration and container data ownership. See [issue #201](https://github.com/aivanov2-godaddy/open-redis-manager/issues/201) and the [synthetic metrics preview](../screenshots/cpanel-podman-live-metrics.png).
- cPanel Jupiter now registers fresh v4 direct-path SVG icons and matching 48×48 PNG fallbacks rendered from the approved ORM mark. Install, upgrade, and uninstall regenerate the theme sprite and synchronize its hash for browser cache refresh. The README logo is unchanged. See the [icon registration record](validation/records/2026-11-20-cpanel-icon-registration.md).
- On-demand fleet status and fresh scheduled-metrics aggregates, plus sequential create/restore batches capped at two visible running accounts with independent audited outcomes.
- Root-only WHM signed-release preview and apply for manually staged bundles: signature and digest verification, explicit conflict-free confirmation, candidate-bound asynchronous transaction jobs, bounded status, and recovery-required reporting. Existing installs must have an exact v3 manifest; v1/v2 manifest adoption only succeeds for an exact match. Apply verifies the installed version, complete managed-file manifest, WHM registration, and the broker's prior service state; when active it also checks the root-owned socket type and permissions. Live disposable cPanel validation remains open.
- Offline release bundle builder for clean, version-matched Git checkouts. It signs bounded metadata with an external RSA private key, derives the public key, validates the archive, and refuses dirty source, unsafe key/output paths, and overwriting an existing bundle. It does not automate publishing or key rotation.
- Optional root-managed provider event delivery signs a fixed allowlist of lifecycle and policy events, queues them locally for bounded retries, and sends them through a separate HTTPS worker. It is disabled by default, requires Perl `IO::Socket::SSL`, and does not send secrets or arbitrary account data. Live receiver delivery remains unvalidated.
- Broker and provider-event systemd units tolerate missing event storage on upgrades; the broker reads provider-event configuration without receiving write access to that file. This avoids service startup failures on installations upgrading from builds that did not create the event paths.
- Signed release metadata v2 binds the exact source commit and declares `state_migrations|none`; the verifier and WHM preview reject unsupported state migrations and display both values before confirmation. Persistent-state transforms require a separate reviewed updater path.
- Exact pre-existing root-owned candidate files missing from an installed v3 manifest can be explicitly reviewed and adopted without rewriting them. Preview and apply require matching fixed path, regular-file type, mode, owner, and signed digest; interrupted recovery preserves adopted files while restoring the prior manifest.
- Root-owned unmanifested files that match the signed candidate after CRLF-to-LF normalization can be explicitly reviewed and normalized to the signed bytes. Apply snapshots the original bytes, and interrupted recovery restores them.
- Root-only report-only security review for fresh fleet memory/client/hit-ratio aggregates, bounded evicted-key and processed-command counter deltas, optional backend authentication-failure counter deltas, and recent normalized ORM AUTH management outcomes. Counter rates require compatible consecutive samples with uptime continuity and actual intervals no longer than 26 hours; reports show interval bounds and treat gaps, missing fields, and resets as unknown. Backend authentication counters are anonymous aggregate evidence and do not identify clients or establish an attack. Operation and authentication activity is not classified as abuse. Requests are limited to one per minute and report events contain fixed metadata only; credential-strength findings remain unavailable.
- Version-six root WHM provider policy with validated global defaults, package client/database ceilings, and opt-in account-create provisioning. New instances cap generated client and database settings at the effective package limits; later over-cap client increases follow report-only, warn, or enforce mode while unchanged or reduced legacy values remain allowed. Version-one through version-five policies migrate with compatibility ceilings, and existing packages migrate with automatic provisioning disabled. New version-three instance manifests capture database, retention, and snapshot defaults; Redis/Valkey config and history collection apply them without rewriting existing instances. Metrics history supports 7–90 days within the 2,160-sample and 1 MiB caps.

## Experimental

- Manual development installer, authenticated cPanel/WHM entry points, and root-owned broker integration. Linux CI exercises fresh-install success and rollback with isolated mock cPanel registration utilities. Current-source install, repeat install, uninstall, repeat uninstall, and reinstall passed on one disposable cPanel host; the supported-host matrix, upgrades, populated ORM data preservation, and full live lifecycle remain open. See the [sanitized lifecycle record](validation/records/2026-11-22-current-source-install-lifecycle.md).
- Optional cPanel account-level Redis AUTH enable, disable, and password rotation for running ORM instances. Generated passwords are returned once after restart and PING verification; failed verification attempts a configuration and service rollback. WHM-directed credential management and disposable-host validation remain open.
- ORM-managed lifecycle, metrics, backups/restore, migration, WHM diagnostics, provider controls, and recovery behavior (including config rebuild/reset) remain experimental on cPanel. EA Podman start/stop/restart passed both one account-context PHP CLI smoke and one authenticated cPanel SSO form smoke on a single disposable host. Cross-account web stop attempts were denied in both directions for Redis caches on one source-matched host, with owner-context PINGs passing afterward. Repeated GETs in one SSO session sometimes omitted the Podman section; normal browser reload/action behavior remains unverified. Valkey web lifecycle, direct ORM service lifecycle, recovery, and broader host coverage remain unverified. See the [sanitized web lifecycle record](validation/records/2026-11-21-cpanel-podman-web-lifecycle.md) and [two-account isolation record](validation/records/2026-11-21-cpanel-podman-web-isolation.md).
- The cPanel health guidance thresholds are heuristics and remain unverified on a supported disposable host.
- The WHM security report is not validated on a supported disposable host; it does not enforce policy and does not claim to detect Redis login attacks, weak passwords, or password reuse.
- Host support across cPanel/WHM versions, supported OS releases, internal PHP versions, EasyApache/Alt-PHP, handlers, CageFS, and PHP Selector.

Three live cPanel account-identity smoke runs passed during private testing. The latest identity run was read-only; its deployed source revision was not matched to the current checkout, and it did not detect a Redis/Valkey backend at the supported common paths. A separate exact managed-v1 package upgrade passed on one owner-designated cPanel test system; that result is recorded independently and does not establish broad update or host support. The identity runs do not validate service lifecycle, ACL behavior across releases, backup/restore, Redis-to-Valkey migration, recovery, or uninstall. See the [host validation matrix](validation/compatibility-matrix.md).
