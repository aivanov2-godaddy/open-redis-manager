# Security model

## Trust boundaries

1. **cPanel user:** may inspect and operate only their own instance and backups.
2. **WHM administrator:** may perform explicitly authorized server-wide operations.
3. **Privileged service:** owns process and configuration changes; it accepts validated structured requests rather than arbitrary command strings.
4. **Redis/Valkey process:** is isolated by account and bound to a private local interface unless a future feature is explicitly designed for remote access.
5. **Provider integrations:** receive minimal, signed events and cannot control the plugin by default.

## Required controls

- Enforce cPanel account identity server-side on every read and write; never trust a submitted username.
- Apply WHM ACL checks and CSRF tokens to all state changes.
- Invoke fixed executable paths with argument arrays; do not concatenate shell commands from request values.
- Validate ports, memory limits, database counts, eviction policies, package IDs and backend identifiers against allowlists and provider limits. Current cPanel memory, client and timeout ranges are broker-enforced request bounds; root WHM package memory ceilings add per-package provisioning/configuration enforcement. Reseller quotas are checked against trusted OWNER metadata and root-owned managed-instance manifests while provisioning is serialized under a root-owned lock.
- Store credentials with restrictive permissions and display them masked. Keep secrets out of logs, audit payloads, diagnostics and support exports.
- Rate-limit authentication-sensitive and expensive operations. Record denial and failure reasons without credential values.
- Score memory use, client counts, evictions, operation rates and optional backend authentication-failure counter deltas as report-only signals. Authentication counters are discovered at runtime, are stored only as root-owned numeric baselines, and must remain monotonic within a bounded uptime-continuous interval. They identify neither a client nor attacker intent; they never trigger a lockout or service action. Provider policy may separately choose warn or enforce for its configured package limits. Exposure tiers change rendered visibility only; broker authorization is unchanged.
- AUTH generation uses a high-entropy secret. ORM does not implement failed-authentication lockout or weak/reused password detection.
- Audit root actions, credential rotation, restore, recovery, backend changes and policy changes without recording credential values.
- Treat provider branding as untrusted display input: accept only bounded plain text, HTTPS support links, structurally validated PNGs, and contrast-checked theme colors; escape all rendered values and send only branding fields through the account-scoped broker response.
- Perform backup, validation and rollback before operations that can interrupt a running service or replace data.

## Data handling

Metrics are limited to the latest numeric sample and hourly history, stored in root-owned `0600` files for at most 30 days; account users cannot read or modify those snapshots. Separate root-owned `0600` counter snapshots keep only current monotonic baselines and bounded numeric deltas, and are overwritten on collection; they contain no usernames, client addresses, keys or credentials. The cPanel diagnostics export uses a fixed allowlist and omits account names, hostnames, paths, credentials, authorization headers, private keys, session IDs, user application content, logs and command output. It is rendered from the verified account's broker response in memory, served with no-store headers, and not retained by ORM. No licensing or telemetry endpoint is required for the open-source core.

The reference product also describes signed commercial licensing and billing lifecycle automation. ORM keeps licensing optional and outside the service-control core; neither commercial licensing nor WHMCS automation is implemented.

## Implemented lifecycle boundary

The browser prototype renders sample data. The installed cPanel page obtains the username from LiveAPI and cross-checks it with a local broker. The broker reads the connecting process UID from Linux `SO_PEERCRED`, maps it through the system account database, and accepts only a matching root-owned cPanel account record. Its fixed operation set provides identity, instance status, live metrics, provision, bounded configuration, start/stop, and account-scoped backup list/create/restore. Account-scoped cPanel requests never contain usernames, paths, commands or backend IDs; initial provisioning can carry only a fixed preset ID, restore carries one strict opaque snapshot ID, and configuration changes carry a strict typed schema. Root-only WHM fleet requests can carry a validated account name and one fixed action. Clients close the request half of the socket before the broker dispatches one complete frame.

WHM writes the selected Redis or Valkey backend to a root-owned policy file. The broker derives all instance paths from the authenticated peer account, writes root-owned configuration and metadata, and starts only `orm-instance@<account>.service`. The systemd template runs the server as that cPanel account, allows only Unix-domain sockets, applies resource limits, and grants write access only to that account's mode-0700 data directory. TCP is disabled and persistence is off by default. Optional Redis AUTH is disabled by default; the cPanel owner can enable, disable, or rotate AUTH for a running instance. Generated passwords use 32 random bytes and are written as `requirepass` in the root-owned `redis.conf` (mode `0640`, account-group readable), because same-account applications need to authenticate. The broker restarts the service, verifies PING with the resulting state, and returns a generated password only in the successful explicit enable/rotation response. On failed verification it attempts to restore the prior config and service. These actions briefly interrupt access; successful rotation invalidates the previous password. AUTH does not replace the private socket/account boundary: code running as the cPanel account can read that account's config and password. WHM has no AUTH controls. Explicit snapshots are created by the root broker in `/var/lib/orm-instances/.orm-backups`: the shared directory is root-owned mode `0711`, each account directory is root-owned with that account's group and mode `0750`, and snapshot files are root-owned with that group and mode `0640`. The account can list and read its files but cannot replace them or modify the shared namespace. Uninstall refuses to remove ORM when any instance metadata or backup remains.

Each AUTH rotation attempt asks syslog's `authpriv` facility to record only the actor UID, account, fixed `auth.rotate` action, normalized result, and service state. The record never contains the password. Logging is best effort; the current cPanel response does not report whether syslog accepted the event.

The account owns its Redis-compatible process and can issue Redis commands through its own private socket. The cPanel form and broker constrain saved ORM settings, but they do not prevent an account from changing its own runtime values directly; those runtime changes may differ from the root-owned config file until the service restarts. The systemd unit's 96 MiB memory limit and 256 file-descriptor limit remain operating-system backstops. Package and reseller enforcement applies only to broker-managed provisioning/configuration and must be validated on supported disposable cPanel hosts before production use.

The WHM fleet inventory is root-only. The broker enumerates validated ORM metadata directories, resolves each name through the system account database and trusted cPanel account file, and reuses manifest validation before reporting normalized state and backend. The configured total counts only verified account records; service-state counts are computed for the visible page only. Separate root-only operations accept only a validated account name and one of the fixed actions; Redis-to-Valkey migration additionally requires the sole target `valkey` and an explicit writer-quiescence acknowledgement. Root WHM diagnostics accept only a selected account name, require a running ORM instance, and execute fixed `PING`, `INFO server`, `INFO memory`, `INFO clients`, `INFO stats`, and `DBSIZE` operations through the validated Unix socket. Only a bounded version and numeric allowlist reaches the UI; database size refers to database 0. The operation is rate-limited per account to one request per five seconds, and arbitrary Redis command text is never accepted. Recovery scans verify one selected account's manifest and normalized service state, then use only `PING` for a running-service health check. They suggest the fixed `start` repair only for verified stopped/failed instances. A repair performs a fresh scan and rechecks manifest/state under the per-instance lock before invoking the fixed systemd start operation. Scan and repair events record actor UID, target account, action class, result and normalized state to syslog's `authpriv` facility without command output, metrics values, or credentials; retention follows host syslog policy. Migration is limited to Redis 6.2–7.2 and Valkey 7.2+, serializes with other per-account operations, creates a safety snapshot, validates it, checks service health and key/expiry counts, and attempts rollback on failure. Exact key contents are not compared, so application writers must remain stopped through verification. Denied non-root attempts use the kernel peer UID and the same facility. Responses contain only the target name, fixed action, normalized state, backend identifiers, validated counters or snapshot IDs, and audit-write status. Non-root peers cannot invoke fleet operations.

Mutations require POST requests on a ten-digit `cpsess`-tokenized route, which cPanel/cpsrvd validates before executing the page; the application guard rejects missing or malformed tokenized routes. WHM fleet controls, diagnostics, backup, recovery, and migration requests also use this guarded route. Initial setup presets, bounded existing-instance configuration, live/stale metrics and hourly history, optional cPanel account-level AUTH enable/disable/rotation, root-only per-account WHM lifecycle, diagnostics, snapshots and Redis-to-Valkey migration, account-scoped RDB snapshot creation/list/download/restore with three-item retention, guarded recovery scan/start, and the cPanel account's minimal previewable diagnostics export are implemented. AUTH status returns only a configured boolean; diagnostics export that boolean (or `null` if unknown), never the password. The one-time password is not retrievable from status; if lost, rotate it again. WHM backup, diagnostics, recovery and migration actions are individual per-account requests with scoped rate limits, bounded result receipts and audit events; a synchronous all-fleet batch remains unimplemented. History requests allow only 24-hour or 7-day ranges; each timer runs the fixed collector as the matching cPanel account, uses only the local Unix socket, and writes root-owned mode `0600` data through an atomic bounded store. The cPanel diagnostics export accepts only a verified account's explicit GET request and selects fixed fields from the broker's validated response; it exports no host/account names, paths, passwords, keys, values, payloads, sessions, logs or command output, and is never retained server-side. Restore accepts only a snapshot ID, runs a fixed backend RDB checker as the account UID, uses a shared backup/restore lock, creates a safety snapshot, and replaces the data file with restrictive account ownership and mode. It verifies service state and attempts rollback if startup fails; each result is audited without credentials. Migration snapshots the running Redis instance, validates the RDB using Valkey tooling, updates only that account's manifest, verifies a Valkey start and key/expiry counts, and attempts to reinstate Redis from the retained snapshot on failure. Exact key contents, provider application-writer state, and supported live cPanel combinations are not yet independently verified; recovery, migration, and other privileged paths remain behind a disposable-host release gate. The backup client runs only a fixed discovered executable with argument-array inputs, a 60-second deadline, and a 128 MiB output ceiling; command output is discarded. Disposable-host validation remains required before production use.

The broker uses Linux's `SO_PEERCRED` Unix-socket option to read the peer credentials ([`unix(7)`](https://man7.org/linux/man-pages/man7/unix.7.html)). Its systemd unit uses a private runtime directory and filesystem restrictions ([`systemd.exec`](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)).

The root-only audit view accepts POSTed filters on the guarded WHM session route. It queries `/usr/bin/journalctl` through a fixed argument vector for the two ORM authpriv identifiers, with a seven-day range cap, a three-second timeout and a one-megabyte output cap per source. It returns recognized event fields only, and JSON exports cannot carry raw journal messages or extra row fields. Unavailable, truncated, or unrecognized source rows mark the view incomplete. The view does not cover cPanel provisioning, configuration, start, or stop activity, and host journal retention/forwarding determines record availability; it is not a complete host audit trail.
