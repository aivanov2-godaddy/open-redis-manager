# cPanel and WHM entry-point scaffold

This folder contains the cPanel and WHM registration files, authenticated UI entry points, and the first manual installer lifecycle for Open Redis Manager:

- `cpanel/install.json` registers the ORM group with a 32×32 SVG and the launcher with a 48×48 SVG plus a same-name transparent PNG fallback. Jupiter uses the SVG as the primary launcher asset, with PNG fallback, as recommended by cPanel. Both SVGs use pixel-sized viewBoxes: cPanel's sprite installer rewrites rectangle dimensions to the icon's pixel size, so a larger coordinate space clips the red tile. The SVG and PNG files preserve the approved logo artwork. Both use fresh `orm-cpanel-*-v2` filenames to give cPanel distinct sprite asset identities after it retained an earlier icon. The main README brand mark is unchanged. The local [asset preview](../screenshots/previews/cpanel-registration-icons.png) shows the packaged cPanel glyphs.
- `cpanel/files/orm/index.live.php` uses cPanel's LiveAPI PHP class and its session header/footer, compares the LiveAPI username with the local broker identity, and shows only that account's private socket path and PHP, Node.js and Python client examples.
- [`../src/Orm/Cpanel/DiagnosticReport.php`](../src/Orm/Cpanel/DiagnosticReport.php) builds the cPanel support preview/download from fixed, validated fields; the installer deploys it alongside the other account-facing PHP helpers.
- `systemd/orm-broker.service` runs the broker as root. Its fixed local protocol exposes identity, per-account instance status/provision/start/stop, a UID-0-only paginated fleet inventory, and a UID-0-only control request with a validated cPanel account name plus one of three fixed lifecycle actions. It accepts no command, path, unit name, backend or arbitrary configuration values.
- `systemd/orm-instance@.service` runs each Redis-compatible process as its cPanel account, with an account-private Unix socket, TCP disabled, bounded resources, and access only to that account's data directory.
- `systemd/orm-metrics-collect@.timer` schedules hourly history collection while the matching instance runs; its oneshot service executes the fixed Unix-socket collector as that cPanel account.
- `src/Orm/Broker/InstanceManager.pm` verifies root-owned metadata and derives service/data paths only from the authenticated account mapping.
- `whm/open_redis_manager.conf` registers a root-level WHM AppConfig entry guarded by `acls=all`.
- `whm/cgi/addon_open_redis_manager.php` renders the WHM interface and repeats an ACL check before showing it.
- `cpanel/icons/` and `whm/icons/` hold original ORM registration artwork.
- `install.sh` installs the cPanel link and WHM discovery page from this checkout.
- `upgrade.sh` is a guarded compatibility bridge for the exact identity-only install manifest in `legacy/identity-v1/`. It refuses unknown or modified files and any existing instance roots, drains active broker requests, prepares only secure empty instance roots required by the broker sandbox, reapplies cPanel registration through `install_plugin` without first removing its existing feature IDs, rolls back package files and registration on failure, and preserves the broker's enabled/active state. It removes transaction-created roots on rollback only when they remain unchanged and empty, and retains recovery files if rollback fails. This is not a general updater for later releases.
- `apply-release.sh` is the root-only transaction engine for signed, conflict-free v3 file updates. WHM queues it asynchronously through the installed worker after a fresh preview and explicit root confirmation. The worker binds the accepted candidate version and artifact digest, while the transaction preserves Redis/Valkey data and backend selection and keeps durable recovery material. It refuses unsupported migrations and registration changes. The updater still needs live disposable cPanel validation before production use; see the [update preview guide](../docs/guides/update-preview.md), [update lifecycle guide](../docs/guides/update-lifecycle.md), and [recovery guide](../docs/guides/update-recovery.md).
- `recover-release.sh` lists retained transaction IDs, validates an exact recovery preview, and requires explicit confirmation before restoring a signed update's old managed files. It validates all journal, manifest, backup, and target digests before mutation, can resume safely after its own interruption, and never touches instance data or backend policy. Use the same source revision that created the retained transaction if the installed recovery command is unavailable.
- `build-release.sh` assembles the exact required-file payload from a clean, version-matched Git checkout, creates bounded metadata and an archive, signs the metadata with an offline RSA private key, derives the public key, and validates the result. It refuses dirty source, private keys or output inside the repository, weak or broadly readable keys, and overwriting an existing bundle. The private key is never copied into the bundle. See the [offline release signing guide](../docs/guides/release-signing.md).
- `adopt-install-manifest.sh` performs a metadata-only v1/v2-to-v3 conversion when the exact installed file set matches this checkout. V2 must also record the current package version. It refuses modified or older file sets, does not update code, and is required before v1/v2 installations can use the signed release preview.
- `uninstall.sh` unregisters the cPanel link and WHM AppConfig entry, then removes only exact files whose contents match this checkout. A root-owned install manifest verifies deployed file hashes and modes first.
- `lib.sh` contains shared fixed paths, platform checks, and cPanel package assembly.

## Install and uninstall

On a disposable cPanel & WHM server, from the extracted repository root, run as root:

```sh
bash packaging/install.sh
```

To remove it using the same repository revision:

```sh
bash packaging/uninstall.sh
```

The one-time upgrade bridge applies only to the committed identity-only v1 baseline and requires both ORM instance roots to be absent before it starts. It creates the root-owned, mode-0711 metadata and data directories needed by the hardened broker; they contain no instance records or data. On failure it removes only those transaction-created directories that are unchanged and empty. It never installs, migrates, stops, or deletes Redis/Valkey data. Review [`../docs/guides/update-lifecycle.md`](../docs/guides/update-lifecycle.md) before using it.

For an existing v1/v2 install manifest whose complete managed file set already matches this checkout, run `bash packaging/adopt-install-manifest.sh` as root before using the signed release preview. The command verifies the installed hashes, modes, ownership, registration, AppConfig, and package version where present; it changes only the manifest. It refuses older or modified package files and does not perform an update.

New installs and successful identity-v1 bridge upgrades record the package version, installed file hashes/modes, and each file's fixed install target in a root-owned `orm-install-manifest-v3`. Existing v1 and v2 manifests remain readable for compatibility; v1 has no recorded version and neither older schema records the target path. The adoption command can convert only an exact match to this checkout; adopted metadata alone does not provide release authenticity. Signed update support is described in the [WHM update guide](../docs/guides/update-preview.md). Staging, signing-key operations, bootstrap of older installs, and live cPanel validation remain separate release tasks.

These scripts target cPanel's Jupiter theme. The installer checks for Linux, root, Perl, systemd, the cPanel interface files, and the documented cPanel and WHM registration utilities. It refuses file collisions and an existing WHM AppConfig registration. It installs the broker and a per-account systemd template; the broker maps the connecting Linux UID to a safe, root-owned cPanel account record and never accepts account names from the request. It does not install Redis or Valkey packages. A root WHM administrator selects an already-installed backend, and cPanel users can initialize, inspect, start, or stop their own ORM instance. Uninstall compares installed files with this checkout and refuses to continue while any instance entry remains. Keep the matching source revision available for uninstall.

Linux CI exercises fresh-install success and registration-failure rollback against an isolated mock cPanel filesystem and stubbed cPanel/systemd utilities. This does not validate a live install. The live identity evidence is summarized in the [sanitized validation record](../docs/validation/records/2026-11-16-identity-smoke.md): three smoke runs passed, and the latest read-only inventory observed a Podman-managed Redis container. It did not establish the deployed source revision or exercise ORM lifecycle operations. No supported cPanel/WHM version or OS matrix has been established; upgrade validation, WHM AUTH controls, reseller authorization, and broader WHM controls remain open. Optional AUTH can be enabled, disabled, or rotated by the account owner in cPanel. A generated value is shown once after successful enable/rotation. The same account can read its own config and password, and deployment behavior remains unvalidated. Treat this as a development installer for a disposable host, not a production release.

## Current limits

The WHM page checks `REMOTE_USER` against cPanel's reseller ACL before displaying backend discovery or the root-only fleet view, and only root may change the selected backend policy. The policy is root-owned and affects new instances only. The cPanel page compares its LiveAPI username to the broker's kernel-derived peer identity. The broker resolves account operations from `SO_PEERCRED`; its fleet listing requires peer UID 0. Redis TCP is disabled and each socket is private to its account. Optional AUTH is off by default; an account owner can generate or rotate a password from cPanel for a running instance. The value is shown once and stored in the root-owned, account-group-readable config needed by the service. Same-account code can read it, and AUTH does not replace socket isolation. cPanel can edit bounded memory, eviction, client and timeout settings; the account can also alter its own runtime through its socket, so these are not package-level enforcement. Explicit per-account RDB backups are stored under the root-controlled ORM data root, remain readable by that account, and are preserved by the uninstall guard. cPanel restore validates the selected snapshot, creates a safety copy, replaces only the account's RDB, verifies service startup, and attempts rollback on startup failure. Hourly metrics history runs as the matching cPanel account and is stored as root-owned `0600` metadata. A root-only, single-account Redis-to-Valkey migration is implemented with version guards, a safety snapshot, verification and attempted rollback, but it has not passed disposable-host validation. Treat ORM as a development installer, not a production release.

The cPanel `install.json` follows cPanel's documented groups/features model and points to a `.live.php` LiveAPI interface. WHM uses AppConfig with an explicit `all` ACL. The manual scripts in this folder now install the cPanel entry with `install_plugin`, place the interface/code/icon files in fixed documented locations, and register WHM through AppConfig. Uninstall uses `uninstall_plugin` and `unregister_appconfig` and only removes exact matching ORM files. The lifecycle has not been exercised on an actual cPanel server; do not use it on a production server.
